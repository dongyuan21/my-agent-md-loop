# 如何设计一套完整的 Agent 评估体系

面试里如果被问「怎么评 Agent」，一上来就说准确率、召回率、幻觉率，面试官多半会觉得：这人只会评模型，不会评系统。

因为 Agent 评测和传统大模型评测，盯的东西根本不一样。传统评测关心答案对不对；Agent 评测关心的是：任务有没有做成、过程合不合理、系统稳不稳定。用户要的是「生成周报」「分析销售数据」，不是「听起来挺专业的一段话」。

我一般会从下面几件事来看。

## 先看任务有没有完成

这是最重要的指标。用户最终只关心事情办成了没有。要周报就得交得出周报，要建会议就得真的建好。没完成就是没完成，不能靠回答流畅糊弄过去。

## 再看规划靠不靠谱

复杂任务通常要先拆解再执行。比如做竞品分析，正常流程大概是搜资料、提信息、搭框架、再写报告。如果拆解乱了、顺序错了、漏了关键步骤，后面执行再漂亮也白搭。

## 工具调用也要单独看

Agent 很多能力都靠工具。至少得确认三件事：有没有选对工具、参数对不对、时机合不合适。用户查天气，却去调通用搜索接口——这种错一犯，成功率直接掉。

## 别只看结果，也要看过程

两个 Agent 可能都完成了任务，一个三步搞定，另一个调了十次工具绕一大圈。只看最终结果，你永远不知道中间浪费了多少 token 和时间。冗余步骤、错误路径、无效调用，这些都该进评测。

## 完成了，还得看质量

报告准不准、全不全、有没有可执行价值，都要评。可以用人工标注，也可以让大模型当裁判打分，但大模型裁判只能辅助，不能替代人工抽检。

## 上线后会不会崩

很多 Agent 在理想环境跑得很好，一遇到真实用户就跪。模糊表达、信息缺失、工具超时、上下文超长……这些脏输入才是常态。能不能追问澄清、能不能异常恢复、边界情况下还能不能稳住，这一层往往决定真实体验。

## 评测集怎么建

最好的数据来源是线上。从日志里抽真实任务，聚类成场景库；再按理解、规划、工具、执行这些能力补样本，别只堆好做的题。权限不足、工具超时、参数缺失、恶意注入这类边界 case 也要补——线上占比不高，但往往最伤体验。

还有一点：失败样本要持续回流。用户反馈和线上翻车案例沉到评测集里，评测才会跟着产品一起长，而不是建完就吃灰。

## 怎么判定结果

我习惯分三层看：

第一层看任务有没有完成，这是底线。第二层看执行路径合不合理，有没有明显绕路。第三层看最终结果质量，准不准、全不全、能不能用。

这样既能看到最终效果，也能定位中间到底是规划错了、工具调错了，还是生成质量差。

## 和传统评测差在哪

简单对比一下：传统评测看单次回答，Agent 评测看完整任务链路；传统问答案对不对，Agent 问事情办成了没有；传统样本多来自公开基准，Agent 更依赖真实用户任务和线上失败 case。

一句话：传统评测问「答得对不对」，Agent 评测问「事办成了没有，办得稳不稳」。
